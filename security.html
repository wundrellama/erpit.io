Security is part of the product.

ERPit holds a company's books, and vouch holds a customer's personal data. We design both so that the system itself refuses misuse, and every refusal has a name.

Michael Riettini leads development and security at RiRo Enterprises. He is the named contact for security reports, incidents, and misuse alerts.

Report a problem

Send security reports to the security lead.

To report a vulnerability in ERPit, vouch, or a RiRo system, email michael@erpit.io. You can also send a direct message on Urbit to ~dinnyt-divsud, for example with Tlon Messenger.

  • Name the affected component and its version or commit.
  • Give the steps to reproduce the problem, and what you expected to happen.
  • Tell us how to reach you, and whether you want credit.

Test only against your own systems or your own test nodes. Do not test against nodes that other people run.

ERPit and vouch are pre-release. No customer runs them in production yet.

Security work

We defend the systems that we build and run.

Our security work covers the software that we maintain and the systems that we operate:

  • ERPit and vouch. We write and maintain both. Both use the AGPL-3.0-or-later license, and the public repositories open with the first release.
  • RiRo's Urbit nodes. The company's ERPit host, the nodes of our people, and the moons that our AI agents run on.
  • Our AI agent setup. Open-weight models on our own hardware, and the MCP connections between the agents and ERPit.
  • urgit. An Urbit Git host that we contribute to upstream and use every day.

How we use AI models in this work

  • Review of ERPit, vouch, and urgit source code before each merge
  • Analysis and validation of the defects that these reviews find, including their effect on stored records
  • Review of third-party Urbit apps before we run them
  • Investigation of failures on our own nodes

We use AI models for security work only on systems that we own, maintain, or contribute to.

Controls

Security controls built into ERPit.

  • Default deny. The company's ERPit host rejects messages from unregistered nodes before it reads them.
  • Signed events. Each event carries the signature of the Urbit ID that made it. The host checks every event against the permissions of its author.
  • Separation of duties. Nobody can approve their own proposal. The host checks each approval chain when a role is defined, so a chain cannot loop or end without an approver.
  • Agents under supervision. An agent can never exceed its supervisor's permissions. When a supervisor loses a permission, every agent under that supervisor loses it too.
  • Strict input. The host refuses a command that contains a duplicate or unknown key. Thus the text that a person approves and the value that the host signs cannot differ.
  • Less data to steal. The permanent log holds no customer names. A test measures the stored data to prove that a deleted name is gone.

The limit, stated plainly: an Urbit node stores its data unencrypted on disk. ERPit's deployment rules require an encrypted volume for every ERPit host.

Reviews

Every change gets more than one reviewer.

  • Independent builds. More than one AI model builds each milestone task independently. Other models review the results, and a person decides what merges.
  • Review campaigns. In July 2026, a review by several models found 26 candidate defects in ERPit. We confirmed 22 and fixed all 22.
  • Outside review. In August 2026, an outside Urbit developer reviewed the ERPit code. The hardening work from that review merged as 11 pull requests.
  • Tests. ERPit had 1,681 automated tests in September 2026. The tests include checks that each refusal happens, and that it gives the correct reason.

Reported upstream

Defects we found in other projects.

We report the defects that we find in the software we depend on. Each report states the cause and a fix or workaround.

  • Credential isolationNousResearch/hermes-agent#68367Closed as completed, September 2026

    Hermes Agent: a profile inherited another profile's chat credentials

    A backend that the desktop app started for one profile received the chat credentials of a different profile. It then connected a chat platform that its own profile had turned off.

  • Key handlingnarrrl/proton-sdk-rs#2Closed as completed, October 2026

    Proton Drive Rust SDK: one shared folder's key applied to others

    When one request listed several shared folders from the same volume, the SDK used the first folder's key for all of them. The other folders failed to decrypt, and the SDK left them out.

  • Availabilityurbit/urbit#7421Open

    Urbit networking: a latent crash in transfer progress reports

    One function stores a block size of 0, and another function asserts that the stored size matches the real size. A future change that sends real progress data would crash the network event.

Access control we contributed to urgit

  • yapishu/urgit#6, merged: access control for each repository, and pull requests that target a branch
  • yapishu/urgit#14, merged: repository access through membership in an Urbit group. Access fails closed when the group cannot be checked.
  • yapishu/urgit#16, open for review: a CI design. Each job runs in a disposable virtual machine. The required checks come from an approved workflow, not from the change under test.
